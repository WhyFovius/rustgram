# Техническая спецификация форка Telegram на Rust + MD3
## 1. Техническая реализуемость ядра Telegram (Backend & Core)
Для реализации полноценного мессенджера требуется стабильное решение для работы с протоколами Telegram, базой данных и криптографией:

* Базовый движок протокола (tdlib-rs): Оптимальным выбором является кроссплатформенная обертка [tdlib-rs](https://github.com/FedericoBruzzone/tdlib-rs). Она предоставляет автоматическую генерацию типов из файлов Type Language (TL) Telegram и избавляет от ручной сборки тяжелой C++ библиотеки, предоставляя предкомпилированные бинарные файлы для основных платформ. TDLib полностью берет на себя оркестрацию сети, менеджмент сессий, локальное зашифрованное хранилище SQLite и синхронизацию состояний чатов. [1, 2, 3] 
* Альтернатива на чистом Rust (ferogram): Если цель — полностью избавиться от C++ зависимостей, применяется современный асинхронный фреймворк [ferogram](https://ferogram.dev/), работающий напрямую через MTProto и поддерживающий не только текстовые сообщения, но и голосовые/видеозвонки на базе нативных биндингов tgcalls. [4] 
* Асинхронная среда: Вся сетевая подсистема, чтение сокетов и многопоточное скачивание файлов управляются с помощью рантайма tokio, что обеспечивает обработку сотен сетевых событий без блокировки интерфейса. [3, 5] 

## 2. Выбор GUI-фреймворка под Material Design 3 для Telegram

[Material 3 Design Comes To Slint — Slint Blog](https://slint.dev/blog/material-comp-1.0)
[Material 3 Design Comes To Slint — Slint Blog](https://slint.dev/blog/material-comp-1.0)
[Slint | Declarative GUI for Rust, C++, JavaScript & Python](https://slint.dev/)

Для обеспечения бескомпромиссного внешнего вида Material Design 3 (MD3) и высокой скорости работы выбрана библиотека Slint UI (вместо egui):

* Нативная поддержка MD3: Инструментарий [Slint](https://slint.dev/) официально реализует дизайн-систему Material 3 в качестве полноценного дизайн-пакета. Он включает в себя адаптивные сеткиレイアウト, семантические токены цветов Google, поддержку динамического изменения палитры и готовые компоненты (Navigation Drawers, Floating Action Buttons, M3 Badges). [6, 7, 8] 
* Преимущество перед Immediate Mode (egui): Библиотеки типа egui работают по принципу постоянной перерисовки экрана (до 60-120 раз в секунду), что создает непрерывную нагрузку на CPU/GPU и быстро разряжает батарею мобильного устройства. Slint является реактивным фреймворком: графический конвейер спит и производит UI-пасс отрисовки только тогда, когда изменяются внутренние свойства или поступают новые сообщения из ядра Rust. [7, 9] 
* Рендеринг: Разметка компилируется напрямую в высокоэффективный нативный код, использующий аппаратное ускорение через Vulkan, OpenGL ES или Metal. [7, 10] 

## 3. Архитектурный паттерн разделения слоёв в Telegram
Для стабильной работы приложения на мобильных устройствах процессы взаимодействия разделены на изолированные слои:

| Низкоуровневый слой (Rust Core) | Слой UI-Рендеринга (Slint MD3) |
|---|---|
| Парсинг входящих бинарных пакетов MTProto и расшифровка сообщений | Подписка на реактивные свойства (Properties) модели данных чата |
| Оптимизированный хэндлинг файлов: докачка медиа-слайсов, кэширование на диск | Ленивая отрисовка списков (Virtual ListView): рендерятся только видимые пузыри сообщений |
| Фоновое выполнение криптографических операций с использованием инструкций процессора | Анимация переходов между экранами, эффекты нажатия (Ripples) и смена палитр |

## 4. Структура репозитория (Telegram-only)
Полная конфигурация Cargo-воркспейса, нацеленная на монолитную нативную сборку:

telegram_rust_md3/
├── Cargo.toml                  # Настройки воркспейса и флаги оптимизации (LTO, codegen-units)
├── .cargo/
│   └── config.toml             # Включение инструкций процессора (ARMv8 AES / SHA-256)
├── crates/
│   ├── tg_core/                # Ядро взаимодействия (tdlib-rs / ferogram)
│   │   ├── Cargo.toml
│   │   └── src/
│   │       ├── lib.rs          # Точка входа в библиотеку ядра
│   │       ├── client.rs       # Управление жизненным циклом MTProto-соединения
│   │       └── storage.rs      # Интерфейс к локальной БД и медиа-кэшу
│   └── ui_theme_m3/            # Кастомизация токенов и шрифтов Material Design 3
│       ├── Cargo.toml
│       └── src/lib.rs
└── apps/
    ├── telegram_mobile/        # Сборка под Android / iOS via cross-compilation
    │   ├── Cargo.toml
    │   └── src/main.rs         # Инициализация рантаймов и запуск реактивного цикла Slint
    └── ui/
        ├── main_window.slint   # Главный экран (список диалогов, боковое меню M3)
        ├── chat_view.slint     # Окно переписки с поддержкой жестов прокрутки
        └── components/
            ├── bubble.slint    # Кастомный элемент пузыря сообщения (M3 Shape токен)
            └── top_bar.slint   # Шапка чата с динамическим цветом (M3 Surface)

## 5. Оптимизация энергопотребления (Активный режим и Фон)
Энергопотребление — критический фактор для мобильного клиента. Оптимизация достигается на трех уровнях:

   1. Аппаратное ускорение криптографии: При компиляции под мобильные процессоры (aarch64) через .cargo/config.toml принудительно активируются флаги aes_armv8 и аппаратная поддержка SHA-256. Это ускоряет операции шифрования протокола MTProto примерно в 15 раз, радикально сокращая время бодрствования процессора (CPU Wake Time) и снижая нагрев устройства.
   2. Пассивный фоновый режим (Push-First): Постоянное удержание открытого TCP-сокета в фоне блокирует переход процессора в глубокий режим сна (Doze Mode на Android) и приводит к быстрому уничтожению процесса операционной системой. Архитектура приложения использует push-уведомления (FCM для Android / APNs для iOS). Полноценный сетевой стек Rust спит до тех пор, пока нативная ОС не разбудит его при поступлении push-пакета для быстрой фоновой синхронизации. [11, 12, 13, 14, 15] 
   3. Управление сервисами: При необходимости жесткого удержания соединения (например, во время скачивания тяжелого файла в фоне) на Android разворачивается Foreground Service с постоянным системным уведомлением и флагом START_STICKY, что защищает процесс от системного чистильщика памяти. На iOS для периодической фоновой проверки применяется BGTaskScheduler. [14, 15] 

## 6. Карта реализации полного функционала Telegram
Для обеспечения 100% паритета функций с официальным клиентом используются проверенные библиотеки экосистемы:

* Секретные чаты (End-to-End Encryption): Реализуются нативно через криптографические примитивы TDLib или связку крейтов aes + dh-exchange на Rust, гарантируя строгое соблюдение спецификаций MTProto.
* Голосовые и видеозвонки: Интеграция библиотеки WebRTC и обертки над tgcalls (используется в ferogram) для захвата аудио/видео потоков с аппаратных кодеков смартфона и их передачи с минимальной задержкой.
* Управление медиапотоками: Проигрывание аудио, видео и голосовых сообщений на лету с помощью декодеров, интегрированных в пайплайны ядра, без необходимости предварительного скачивания всего файла на диск.
